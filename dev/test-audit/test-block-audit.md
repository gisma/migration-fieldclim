# Test block circularity audit

## Scope

This audit classifies every individual `test_that()` block in `tests/testthat/` by test purpose, expected-value basis and circularity risk. It is observational only: no package source, tests, documentation, vignettes or metadata were changed.

The shared fixture file `helper-physics-fixtures.R` contains no `test_that()` blocks and is not counted in the block totals.

## Classification rules

- A. independent equation-contract test
- B. helper equation-contract test
- C. API parity / wrapper consistency test
- D. guard / edge-case behaviour test
- E. workflow / integration test
- F. smoke / coverage test
- G. potentially circular or weak test

- Strong: expected value is independently computed from documented equations, explicit constants, or independently specified reference values.
- Acceptable: verifies API routing, wrapper parity, object behaviour, guard behaviour, fallback behaviour, or workflow fields without claiming physical correctness.
- Weak: only checks that code runs, that an object exists, or compares wrapper outputs without a clear contract.

- Low circularity: expected value is independently computed and does not call the function under test.
- Medium circularity: expected value uses upstream helpers, closure identities, or paired package functions.
- High circularity: expected value comes from the same function, a wrapper around the same function, `turb_flux_calc()` output, or direct-vs-`weather_station` equality when read as physics.

## Interpretation

- 41 blocks provide strong evidence that implementation matches documented equations, explicit constants, or independently specified reference values. These are the blocks most useful for code/documented-equation consistency.
- 62 blocks primarily support wrapper/API/workflow behaviour. These are valuable regression tests, but their expected values often come from direct methods, wrappers, object fields or workflow outputs.
- 3 blocks are smoke/coverage support or explicitly weak. Most should remain only if they protect plotting, branch coverage, or open-policy boundaries; they should not be cited as physics validation.
- Closure tests are useful and should remain, but they have medium circularity unless the partition formula itself is reconstructed independently.
- Direct-vs-`weather_station` equality tests are useful API parity tests. They are high circularity for physics because the direct method is the oracle.
- `turb_flux_calc()` tests are workflow/integration tests. They verify orchestration, fallback and field addition, not the physical correctness of the methods called inside the workflow.

## Recommendations for future test work

- Keep API parity tests, but label them as wrapper contracts in comments when they might be mistaken for formula validation.
- Strengthen smoke-only plot/coverage blocks only if a stable output, error, warning or object contract can be asserted.
- For any future equation-contract test that uses upstream helpers, include a comment that the helper is not the function under test and is separately covered.
- Do not remove closure tests; pair them with independent formula tests where source/documented equations are available.
